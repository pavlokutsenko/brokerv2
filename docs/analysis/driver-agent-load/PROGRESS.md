# Driver-assisted agent loading (2026-09-23)

Later proxy and early-load experiments are recorded in `../proxy-routing/README.md` and `../early-agent/README.md`. The proxy remains incomplete; this file preserves the earlier driver and GUI-hook work.

Goal: remove executable-adjacent `version.dll` while keeping the existing user-mode HWID/proxy agent and the receive-hook session. HardShift's exact injection sequence is still unconfirmed; this is an independent implementation.

## Evidence

- The verified LU4Memory protocol 3 driver already supports bounded target memory allocate/write/protect/free. It has no agent-loader IOCTL.
- A benign child process loaded the agent through driver-allocated path memory and `CreateRemoteThread`; the full identity/HTTP CONNECT smoke passed.
- On a live LU4 PID, `OpenProcess` returned a handle, but `NtQueryObject(ObjectBasicInformation)` showed `GrantedAccess=0x001FF405` after requesting `0x001FFFFF`; `PROCESS_CREATE_THREAD` and VM rights were removed. `CreateRemoteThread` failed Win32 5 and `NtCreateThreadEx` returned `0xC0000022`. `OpenThread(THREAD_SET_CONTEXT)` returned a handle with `GrantedAccess=0`, and `QueueUserAPC` failed. The failed template launch terminated its owned PID. A separate direct-launch test PID 17480 was stopped before driver replacement.
- The candidate driver added only `IOCTL_LU4_OPEN_AGENT_PROCESS` at function 0x80D. It returned a caller-owned target-process handle using `ObOpenObjectByPointer` after checking requestor/current process identity. This was meant to avoid the observed access stripping. Existing protocol version and IOCTLs remained intact. Candidate build succeeded, SHA-256 `E5B72D346B5C1A81D6F933AB880BFD292CDE8272A28AA088FB9482701E3E8787`. The verified artifact with hash `2393EEE0E77E03A3C5D4640CE16F0A6AC1B6DE1E1A3D7887B1635AE6186AE766` was not changed.

## Result and rollback

- The candidate passed the benign child smoke, including identity hooks and authenticated HTTP CONNECT.
- On protected LU4, its returned handle had `GrantedAccess=0x00001400` after requesting `0x043A`. `CreateRemoteThread` failed Win32 5. The candidate IOCTL does not bypass the game's process-object callback. No agent-ready event was emitted.
- Test PID 4580 was stopped. The candidate service was stopped, its path was restored to the verified release binary, and the verified driver was started. The loader log confirms that it restored the original DSE value `0x2006`. The verified binary hash remains `2393EEE0E77E03A3C5D4640CE16F0A6AC1B6DE1E1A3D7887B1635AE6186AE766`.
- The failed IOCTL and application loader were removed from the shipping source. The working `version.dll` startup path remains in place while another driver execution mechanism is investigated. The candidate `.sys` remains only as a local build artifact; it is not in the release package.

Do not promote this candidate or assume that HardShift uses the same `CreateRemoteThread` sequence. Its observed live path is recorded in `../hardshift-launch/README.md`.

## Follow-up feasibility check

- Installed OS is Windows 10 Enterprise LTSC build 19044. The local `ntoskrnl.exe` exports `KeInitializeApc` and `KeInsertQueueApc` but not `NtCreateThreadEx`, `ZwCreateThreadEx`, or `ZwQueueApcThread`. The WDK does not declare the APC insertion routines as supported driver APIs. Microsoft's `PsCreateSystemThread` documentation says its threads have no user-mode context, so it cannot directly run `LoadLibraryW` in the client. Ordinary user APC delivery requires an alertable user-mode wait; no such target thread has been confirmed in LU4. Sources: [PsCreateSystemThread](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/nf-wdm-pscreatesystemthread), [Waits and APCs](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/waits-and-apcs).
- A direct launch of `lu4-win64-shipping.exe` (test root PID 7012) was sampled for `PROCESS_CREATE_THREAD | VM_OPERATION | VM_WRITE | VM_READ | QUERY_INFORMATION` access during its first roughly three seconds. `OpenProcess` failed in 27 samples; no usable root-process handle was demonstrated. The test root and child exited or were stopped, and no client remains from that probe. This does not justify a root-process user-mode loader.
- The HardShift agent-load wrapper passes a PID and two DLL path slots through IOCTL `0x222140`, but its manually mapped `hscore-driver` handler is not available as a local file. Targeted searches in HardShift's directory, Desktop, AppData, ProgramData and tools found no retained 105,464-byte image. A read-only scan of its live user memory in the preceding run also found no retained PE image. The kernel execution method remains unknown.

## Independent GUI-hook loader

- Exported `PriceCheckHookProc` from our own `PriceCheck.ClientAgent.dll`. A per-thread `WH_GETMESSAGE` hook caused Windows to load this DLL into a benign Notepad process. The same procedure then loaded it into protected LU4 PID 16336 with no adjacent `version.dll`; the agent-ready event was observed while the client stayed alive. This is a Windows GUI hook, not a reproduction of HardShift's unknown kernel loader.
- The collector now waits for the final client's GUI window, installs this hook on its owning GUI thread, posts a harmless `WM_NULL` to trigger it, waits for agent readiness, and removes the hook. The agent pins its own module before enabling MinHook detours so hook removal cannot unload active detour code. In the collector process itself, where no template environment exists, the agent worker exits without installing hooks.
- `tests/ClientLaunch.LiveSmoke` launched a protected LU4 client with a rotating HWID template through `ClientProcessService`. Final PID 11236 reported agent ready, remained alive for 20 seconds after the GUI hook was removed, and had no game-adjacent `version.dll`. The test terminated its own client. `agent-11236.txt` recorded `ready`. No changes to the verified LU4Memory driver were needed; the radar and broker receive hooks still use it separately.
- A second live smoke launched LU4 PID 15192 with the same template, then called the application's `WaitForGameWindowAsync` and `RadarSessionManager.StartAsync`. The driver-backed receive hook installed and produced a radar snapshot. The test removed the radar hook and terminated its own client. The existing native smoke passed all identity probes and an authenticated HTTP CONNECT against its local test proxy after rebuilding the agent.
- A live LU4 launch with both HWID and optional HTTP proxy enabled reached agent readiness (PID 17080), which is emitted only after both hook installers succeed. No CONNECT reached a local test proxy during 40 seconds before login; the client made no observed network attempt in that interval, so end-to-end game proxy traffic remains unverified with this loader. The native smoke directly exercises authenticated CONNECT.
- The GUI hook fires only once the final client has a window and pumps messages. Identity reads performed earlier in process startup are outside this loader's timing. The smoke verified the same launcher and radar services used by the UI; direct UI clicking was unavailable in this session because the computer-use tool returned `coordinate input geometry is unavailable`.

## Login and proxy observation

- Added opt-in, bounded category tracing to the native agent (`PRICECHECK_TRACE_HARDWARE=1`). It records API categories and numeric status codes under LocalAppData; it does not record hardware values, credentials or packet payloads. The benign native smoke still passes identity replacement and authenticated HTTP CONNECT.
- In the no-proxy live run (PID 6812), the user entered a character successfully. The agent and driver-backed radar were ready before login. After agent installation, the instrumented hardware hooks observed successful `GetAdaptersAddresses` calls, including calls around login. They did not observe calls to the other instrumented SMBIOS, registry, disk, volume, or `SendARP` APIs. This is limited to those hooks and that time window; it does not establish all identifiers the game or anticheat reads.
- For an authenticated external HTTP proxy, a separate-process preflight received `HTTP/1.1 200 Connection Established` for the game login endpoint. In protected LU4 with the local relay path (PID 3512), the game's TCP `connect` to the relay returned Winsock `10060` immediately, and the relay accepted no connection. Consequently no HTTP CONNECT was sent from this game attempt. An experimental direct-to-proxy path on the game's socket (PID 8916) also returned `10060` before HTTP CONNECT. The login screen reported a connection error in both runs. Neither experiment demonstrated working proxy traffic in protected LU4.
- The experimental direct-to-proxy mode and listener-address change were removed after these failures. The remaining local-relay mode is still incomplete for this protected game: enabling the optional proxy prevents login in the observed setup. Do not advertise successful LU4 proxy support based on the benign smoke or the proxy preflight. The exact reason the protected game's socket rejects a changed destination is unconfirmed; inspect socket state and relevant network policy before choosing a new transport design.
