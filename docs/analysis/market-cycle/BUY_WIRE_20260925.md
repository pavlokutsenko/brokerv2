# Exact buy-shop replies and missed passing windows, 2026-09-25

The user asked why many queue items were deferred, and specifically rejected
postponing unsupported formats for 24 hours. The experiment was reverted:
server failures still retry after 2/5/15 minutes. A read-only queue audit at
20:20 found 56 deferred and 140 ready buy shops with the old decoder error;
other deferred work included 40 normal sells without a clear route. The exact
buy format was the dominant removable cause.

## Buy wire format

Normal sell and package sell shops use the verified A1 reply. In five preceding
routes, 253 normal sells and 20 package sells were exact; 187 buy shops remained
unverified. The existing route reader temporarily captured all incoming frames
only while a buy reply was pending. This showed opcode `BE` for the same trader
ObjectID. Seven BE examples had one, nine or ten rows and a strict
`17 + 96 * row_count` length. The packet header has ObjectID at byte 1 and count
at byte 13; each row has item ID at offset 4, signed 64-bit price at offset 72
and signed 64-bit requested quantity at offset 88. All item IDs and nearly all
quantities agreed with the fresh broker (two quantities differed between
observations). The first row field is a wire item code, not the ephemeral
`item_object_id` from the client event.

A later live pass with corrected diagnostic metadata matched 47 buy events and
235 rows to exactly one BE reply per trader. Item ID and the low 32 bits of
price and `buy_count` matched the corresponding `PlayerShopBuyItemsList` event.
The exact decoder validates complete framing, row counts, identity, order and
low-bit correspondence before trusting the wire's 64-bit values. The event
supplies enchant, base price and its local row object ID. A synthetic test covers
prices and quantities above 2^31; the observed live buy prices so far were
below that boundary. Other BE variants remain unverified on a failed format
guard.

The first exact-buy route `route-ba0118fb323d4de3ae7bc23a3935b872` read
67 shops before a diagnostic packet-ring overrun. The server accepted all 67
as current snapshots: 33 buys/154 rows, 32 normal sells/165 rows and two package
sells/eight rows. The background outbox drained. The temporary broad packet
capture caused the overrun (`94 > 64`) during a full actor scan; it was removed.
The deployed hook now copies only A1, BE and the previously observed movement /
cancel messages. The next live route `route-4bdb378767ed417e93045a4704c4f9fd`
completed with 88/88 exact shops and no overrun. PostgreSQL marked all 88
current: 40 buys/233 rows, 45 normal sells/232 rows, three package sells/13 rows.
The outbox drained.

## Unrequested passing targets

The preceding route `route-14b4c459c218487aa2be7f299da51f17` read 100
shops but reported 30 failed passing approaches. None of those 30 received a
request; they were missed windows, not rejected shop responses. The full actor
scan took roughly 466 ms near the route end. The 72-unit-offset pass leaves
only a short interval inside the 85-unit interaction radius. The next build
filters the actor scan by ObjectID from the already claimed broker/radar
bindings before reading expensive capsule/name/title fields. Its failure reason
is now `Passing window missed before shop request`. The targeted scan is deployed
in collector PID 2980 from 20:37. Its first completed route reported a last
scan of 81 ms (prior full scan ~466 ms), with 18 missed windows and 11 no-route
targets. These routes have different target geometry, so the change in missed
count alone does not prove a 40% improvement.

Offline planner checks showed no reduction in no-route targets when trying all
24 pass directions instead of the first eight; the change was reverted. Raising
anchor spacing from 150 to 200 theoretically covered more target coordinates
but made the path about 9% longer and slightly increased no-route cases in one
sample. It is not deployed; evaluate only after the current full market pass.

The route progress display now shows live shop/exact counts, rather than a
percentage that can reset when recovery replans the remaining path. The top
server counters still update after route completion and background delivery.
