# V65: время жизни буфера CapsuleTrace, 2026-09-26

## Найденная причина аварийного чтения

V63 PID19296 (Tweedle) упал 20:03:04 при возврате в центр. Сначала Python
получил таймаут ProcessEvent, затем cleanup.stop обнаружил trigger=1/status=0.
WalkClient.close выполнял cleanup_callbacks в finally даже при занятой команде.
PawnCapsuleProbe освободил 64 КБ ActorsToIgnore, хотя команда ещё могла быть
исполнена игровым потоком. Следующая попытка наблюдала trigger=0/status=1.

В сохранённом UE minidump: EXCEPTION_ACCESS_VIOLATION, чтение 0x23088960000,
инструкция lu4+0x341c203, стек проходит через установленный командный thunk.
Тот же указатель находится в TArray на стеке: count=capacity=0x7FF (2047).
Другой кадр содержит адрес params+80: 0x2308891F150 — поле ActorsToIgnore
Pawn CapsuleTrace. capture-state.json старого PID фиксирует command
0x2308891F000 и params 0x2308891F100. Командный heap не включён в minidump;
его содержимое не выдумывалось. Дамп, стек и безусловная очистка показывают
опасный путь освобождения массива до окончания вызова. Причина задержки
первоначального вызова остаётся неизвестной; время жизни массива исправлено.

## Исправление

- PawnCapsuleProbe передаёт освобождение массива WalkClient.release_command_buffer.
- На существующем owned bridge читается только известный header (8 байт).
- Освобождение разрешено при совпадающем PID, trigger=0 и status=0 либо 2.
- Armed, running, неизвестное состояние или ошибка чтения: буфер сохраняется
  до завершения процесса. Ничего не обнуляется и не переписывается в команде.
- Остальные cleanup_callbacks продолжают останавливать reader и восстанавливать
  hook entry points. Их нельзя пропускать вместе с освобождением геометрии.
- V64 при зависшей команде запускает восстановление owned клиента с сохранением
  прохода; завершение процесса освобождает сохранённый буфер штатно.
